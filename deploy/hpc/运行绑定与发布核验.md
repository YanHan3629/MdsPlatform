# 运行绑定与发布核验

本说明适用于产业链账号与受控视图候选。正式账号、数据库、对象、合同、授权、回执和已发布快照须保留；完成验收前不切换正式部署。本文件描述操作要求，不代表当前模型、十二企业前端、全部撤权场景或正式切换已经验收。

## 发布清单

常规 CPU/GPU 启动要求应用目录存在私有的 `runtime-bindings.json`。清单同时约束后端 JAR、九个启动与账号维护文件、五组服务源文件、MinIO 初始化脚本、八个 SIF，以及 Qwen 模型文件。清单须归当前 HPC 用户所有，不可由组或其他用户写入；清单本身不向组或其他用户开放。代码目录使用干净、固定的候选版本，不保留 Python 字节码缓存。

清单记录实际文件 SHA-256。`.verified`、镜像标签、源码目录名及 READY 状态分别保留其原来的含义，不能代替这些字节检查，也不能代替账号、资源范围和合同授权。

在有限 CPU Slurm 作业内，安装和核对已审阅的候选文件后生成一个新的候选清单。下面的路径需填写本次实际版本，不能照抄历史作业号：

```bash
python3 "$APP/runtime_source_binding.py" prepare \
  --app-root "$APP" \
  --source-root "$REVIEWED_SOURCE" \
  --packages-root "$PACKAGES" \
  --model-root "$MODEL" \
  --manifest "$APP/runtime-bindings.candidate-$RELEASE.json"

python3 "$APP/runtime_source_binding.py" verify \
  --manifest "$APP/runtime-bindings.candidate-$RELEASE.json"
```

`APP` 为本次实际应用根目录，`REVIEWED_SOURCE` 为已冻结的完整服务源目录，`PACKAGES` 为已核验的本地 SIF 目录，`MODEL` 为原有 Qwen3.5-0.8B 目录。生成清单不会批准代码、创建业务授权、启动服务或改变模型。生成结果还须与本次审阅的候选文件清单、JAR 和镜像摘要逐项核对。

保留旧清单、旧启动文件和旧程序版本。仅在维护窗口、现有作业已终止且新清单核验通过后，将候选清单原子替换为 `runtime-bindings.json`。此步骤不能与运行中任务的源码替换并行进行。Start 只启动已安装的版本，不上传、不构建、不安装新版本。

## 实际加载方式

- 后端及接收端使用清单中的同一 JAR。
- 检索与 QA 将对应整组源文件只读绑定至 `/candidate`，从该路径启动应用。镜像内的模型数据与已核验依赖继续使用。
- 业务与证据工作器使用清单中的完整源目录及同一组专业解析代码。旧的独立 `evidence-worker.py` 覆盖文件不再决定候选工作器版本。
- 原生索引与受控预览使用由 SIF 摘要和完整索引源文件摘要共同导出的镜像引用。该引用进入后端冻结的任务定义；动态任务在创建、申请 Slurm step 以及 step 内实际执行前复核原清单与源文件。
- 原有显式镜像 ID／引用保留其原镜像内程序，不自动改写用户的历史任务命令。新的受控索引任务使用包含源摘要的新引用；更新索引程序后，旧引用若未另行登记会拒绝执行，须按授权流程重新审核重试。
- 每个会话保留 `runtime-bindings-verified.json`；就绪信息附带非秘密绑定摘要。动态任务的 `image-proof.json` 同时记录 SIF 与源绑定。它们证明加载身份，不证明业务授权或模型回答正确。

Qwen 保持 0.8B、2048 上下文、每次最多两张图像和两条并发序列、GPU 使用率 0.78。vLLM 使用每次会话生成的临时 API key，仅经私有环境文件传递给 vLLM 和 QA；不会写入启动命令参数或就绪信息，退出时删除环境文件。各服务仅在计算节点回环地址监听，经既有 SSH 隧道从 Windows `18888` 访问。

## 账号与撤权边界

程序绑定不授予数据权利。每次读取仍要求账号、企业、操作能力、一个完整的当前资源授权、用途、冻结版本和合同修订均满足约束。平台管理资格不自动开放业务数据。新测试窗口使用新的审核记录，不能通过 SQL 延长旧授权或改写旧视图。

`ResourceLease` 和 `EVIDENCE_IO` 还须绑定最初的完整授权代次，或明确的旧版 FULL_VERSION 合同及修订。旧的不含原始授权绑定的 `EVIDENCE_IO` 凭据应拒绝；不能为兼容恢复其广泛访问能力。账号会话凭据与工作器凭据不互相替代，注销或撤权后的旧工作器凭据不应重新获得访问。

受保护输出须在首次输出前和流式分块期间复核。目标要求撤权后五秒内阻止后续受保护步骤及输出；已经交付给用户的字节无法追回。现有正常 HTTP 流和部分 CPU 工作器组件结果不等于已证明模型、质量、独立交付、授权数据库故障、重启及并发下的完整上界；这些项目须保留独立验收结果。

### V40 自动索引队列升级

升级前在获批维护窗口记录待处理任务 ID、数据集和已发布版本，按发布流程核对数据库备份及新 JAR。V40 会为自动索引任务记录发起会话。升级前入队且缺少该记录的任务，在领取时会以 `INDEX_AUTHORITY_DENIED` 失败，原因是 `INDEX_ORIGIN_SESSION_REQUIRED`。

需要恢复时，由仍有该冻结版本索引权限的用户登录，在对应版本选择「对已发布版本回填」。接口是 `POST /api/mm/datasets/{datasetId}/versions/{versionId}/ingest-tasks/backfill`。回填沿用原任务 ID，并记录当前有效会话。核对原件仍属于同一已发布版本，以及索引任务实际启动后的运行状态。若回填请求超时，先查询该版本的任务列表和原任务 ID，再决定是否重试。

## 失败与回退

缺失清单、未知文件、源文件或 SIF 摘要变化、清单权限错误、JAR 不匹配及 step 内绑定变化均停止启动或任务执行。保留原失败、日志及任务状态，不把应用启动失败标记为业务成功，也不将计算结束等同于 READY。

回退前先停止本轮拥有的有限会话，核实没有遗留活动任务，保留当前失败记录，再恢复已审阅的上一整组程序、源目录与绑定清单。不要单独回退某个工作器或复用新版本清单。数据库新增迁移、业务审计、授权和回执不可通过覆盖旧备份回退；程序不兼容时保持维护状态，准备向前修复。

正式切换仍须先完成 A01–A10、D01–D13、十二个企业在 Edge 经 `18888` 的真实前端、当前实际 Qwen 入模证据，以及正式账号／数据／合同／授权／回执前后核对。独立测试库的启动和下载组件通过，不构成正式切换批准或完整验收。


## V2 官方会话入口校验

V2 运行清单在原有九份运行脚本的基础上，增加 `run_platform.sh`、`session_control.py` 和 Windows `session.ps1` 的逐文件 SHA-256。它们必须与当前发布源码中的对应文件相同；准备新清单时三份文件缺失会失败，运行时内容漂移也会被拒绝。官方 Start、Status、Connect、Stop 使用 `-WorkspaceRoot` / `--workspace-root` 选择同一个私有部署目录，该目录下的实例作业名称与其他部署区分。

新的 `proof()` 输出包含 `bindingSchema`、`operatorControlsCovered` 和 `operatorControlFilesSha256`。V2 必须完整覆盖十二份运行文件。旧 V1 清单继续只接受原来的九份文件，明确报告 `operatorControlsCovered=false`；旧记录不能证明官方会话入口已经纳入校验。清单版本不替代实际启动、初始化、业务、停止和资源释放验收。

本变更不覆盖已有冻结清单，不替换运行中的部署，不改变 JAR、已应用迁移、SIF 或模型字节。切换到新发布目录前仍需完成相应的 CPU/GPU 及操作入口验收。旧应用、数据库、对象和快照按原有保留规则处理，应用文件回滚不等于数据库回滚。
